# الخطوة 2: وكيل العميل المثالي (ICP) — نموذج استدلال ومحادثة

> **دروس الكورس المطبّقة:** 2.6 نماذج الاستدلال · 2.3 إدارة حالة المحادثة · 2.5 المخرجات المهيكلة · وتذكير بالدرس 2.1 (اختيار النموذج حسب المهمة)

## ماذا سنبني في هذه الخطوة؟

**ICP** اختصار Ideal Customer Profile، أي "ملف العميل المثالي": وصف دقيق للشركات التي يجب أن تبيع لها أولاً. في Explee هذه هي الخطوة التي تأتي بعد تحليل موقعك: "هذه الشرائح التي نقترح أن نستهدفها".

الوكيل يقرأ ملف الشركة المحفوظ من الخطوة 1، ويقترح 2–3 **شرائح** (segments)، لكل شريحة: القطاع، والحجم، والمنطقة، والمسمّيات الوظيفية لمن يشتري، والمشاكل التي يحلها المنتج لهم، و**أسباب ملاءمتها مربوطة بحقائق من الملف**، وعلامات يمكن رصدها من الخارج، وعلامات الاستبعاد.

ثم **تحاوره**: "ركّز على البنوك"، "أضف مصر"، "الشركات الصغيرة لا تناسبنا". في كل مرة يعيد التقرير كاملاً مع التعديل، ويشرح ما غيّره.

الناتج:

| الملف | المحتوى |
| --- | --- |
| `data/output/icp_lucidya.com_v1.json`، `_v2`، ... | كل نسخة من المحادثة |
| `data/output/icp_lucidya.com.json` | النسخة النهائية؛ **مدخل الخطوة 3** |

لماذا نحفظ كل النسخ؟ لتقارن كيف تغيّر التقرير مع كل ملاحظة، ولتعود لنسخة سابقة إن لم تعجبك الأخيرة.

### 1. اختر نموذج الاستدلال في `.env`

من جدول النشر عندك في Azure:

تحقق:

```powershell
python -m scripts.check_env
```

يجب أن ترى `Model [reasoning]: gpt-5-mini` و `Reasoning : medium`.

### 2. اسحب التحديث وشغّل الاختبارات

```powershell
git checkout main
git pull

```

45 اختباراً، بينها 7 جديدة.

### 3. شغّل الوكيل

تأكد أن ملف الخطوة 1 موجود (`data/output/company_lucidya.com.json`)، ثم:

## المفاهيم

### نماذج الاستدلال (الدرس 2.6)

النموذج العادي (مثل `gpt-4o-mini`) يبدأ الكتابة فوراً: كل كلمة يكتبها هي جزء من الإجابة. **نموذج الاستدلال** (مثل `gpt-5-mini` و `o4-mini`) يكتب أولاً **تفكيراً داخلياً مخفياً**: يقارن الخيارات، ويراجع نفسه، ويستبعد ما لا يصلح. ثم يكتب الإجابة.

لماذا نستخدمه هنا وليس في الخطوة 1؟

| الخطوة | نوع المهمة | النموذج المناسب |
| --- | --- | --- |
| 1: تحليل الموقع | **استخراج**: المعلومة موجودة في النص، المطلوب إيجادها وتلخيصها | عادي (`smart`) |
| 2: العميل المثالي | **استنتاج وموازنة**: أي الشرائح أفضل؟ لماذا؟ ما الذي نفترضه؟ | استدلال (`reasoning`) |
| 3: تقييم العملاء (القادمة) | **تكرار بسيط**: قارن شركة بمعايير واضحة، مئات المرات | عادي رخيص (`fast`) |

هذا تطبيق مباشر للدرس 2.1: **اختر النموذج حسب المهمة.** الاستدلال أبطأ وأغلى، فلا نستخدمه إلا حيث يلزم التفكير.

### رموز الاستدلال: تفكير تدفع ثمنه ولا تراه

التفكير الداخلي يُحسب **رموز إخراج**، ويُدفع بسعرها، لكنه لا يظهر في الإجابة. السكربت يطبعه:

```
Tokens: 2100 in / 3400 out (of which 2600 reasoning)
```

في هذا المثال، 2,600 من أصل 3,400 رمز إخراج كانت تفكيراً. أضفنا الحقل إلى سجل كل استدعاء في `core/client.py`:

```python
"reasoning_tokens": getattr(out_details, "reasoning_tokens", None),
```

فتستطيع مقارنة تكلفة التفكير بين الخطوات والإعدادات.

### التحكم في عمق التفكير: `reasoning.effort`

```python
return {"reasoning": {"effort": config.REASONING_EFFORT}} if config.REASONING_EFFORT else {}
```

| القيمة | متى يُستخدم | الاعتبارات |
| --- | --- | --- |
| `minimal` | مهام بسيطة تحتاج سرعة (عائلة `gpt-5` فقط) | تفكير شبه معدوم |
| `low` | موازنة بسيطة | أسرع وأرخص |
| `medium` | الافتراضي؛ مناسب لـ ICP | توازن |
| `high` | قرارات معقدة بعوامل كثيرة | أبطأ بكثير، رموز تفكير أكثر |

جرّب نفس الملف بمستويين وقارن الجودة ورموز الاستدلال:

```powershell
python -m scripts.define_icp lucidya.com --effort low --feedback ""
python -m scripts.define_icp lucidya.com --effort high --feedback ""
```

(`--feedback ""` يعني: الاقتراح الأول فقط، دون محادثة.)

**ثلاثة فروق عملية مع نماذج الاستدلال:**

1. **لا تقبل `temperature`.** لذلك لا نرسلها في هذه الخطوة (الاختبار `test_propose_sends_profile_to_reasoning_model` يتحقق من ذلك).
2. **النماذج العادية ترفض المعامل `reasoning`.** إذا وضعت `MODEL_REASONING=gpt-4o-mini`، اترك `REASONING_EFFORT=` فارغاً، فيعمل الوكيل بلا استدلال (مفيد للمقارنة).
3. **قد تنفد الرموز في التفكير.** إذا فكّر النموذج طويلاً ووصل حد الرموز قبل كتابة الإجابة، يكون `status` مساوياً `incomplete` و `output_parsed` فارغاً. رسالة الخطأ تقترح `REASONING_EFFORT=low`.

### حالة المحادثة: `previous_response_id` (الدرس 2.3)

في الخطوة 1ب، حلقة البحث كانت **تعيد إرسال كل التاريخ** في كل دورة: نحن نحمل قائمة `items` وتكبر. هذه طريقة، وهناك طريقة ثانية يعلّمها الدرس 2.3: **الخادم يحفظ المحادثة**، ونحن نشير إليها برقم.

الدورة الأولى ترسل الملف كاملاً، وتطلب من الخادم حفظ الاستجابة:

```python
response = ask(
    "Company profile:\n" + profile.model_dump_json(indent=2),
    task="reasoning",
    instructions=INSTRUCTIONS,
    text_format=ICPReport,
    store=True,
    ...
)
```

كل دورة لاحقة ترسل **الملاحظة وحدها** ورقم الاستجابة السابقة:

```python
response = ask(
    feedback,
    task="reasoning",
    instructions=INSTRUCTIONS,
    text_format=ICPReport,
    previous_response_id=previous_response_id,
    store=True,
    ...
)
```

الخادم يستعيد بنفسه: الملف، والتقرير السابق، وكل الملاحظات قبلها، و**تفكير النموذج السابق** أيضاً في نماذج الاستدلال.

| | نحن نحمل التاريخ (الخطوة 1ب) | الخادم يحمله (هذه الخطوة) |
| --- | --- | --- |
| ماذا نرسل في كل دورة | كل التاريخ | الجديد فقط + رقم |
| حجم الطلب | يكبر في كل دورة | صغير دائماً |
| **رموز الإدخال المدفوعة** | كل التاريخ | **كل التاريخ أيضاً** |
| يعمل مع `store=False` | نعم | لا |
| التحكم في التاريخ (حذف، تعديل) | كامل | لا |

**السطر المهم في الجدول:** `previous_response_id` **لا يوفّر المال**. الخادم يمرر كل المحادثة السابقة للنموذج، وتُحسب كلها رموز إدخال. ستلاحظ أن `input_tokens` تزيد في كل نسخة. الفائدة أنك لا ترسل ولا تدير التاريخ بنفسك، وأن تفكير النموذج السابق يُحفظ.

**فخ مشهور:** `instructions` **لا تنتقل** من الدورة السابقة. إذا لم ترسلها في كل دورة، يعمل النموذج في الدورة الثانية بلا تعليماتك. وكذلك `text_format` لأنه جزء من الطلب وليس من المحادثة. لهذا يرسلها `refine_icp()` في كل مرة، والاختبار `test_refine_sends_only_feedback_plus_previous_id` يتحقق من ذلك.

**Azure:** الاستجابات المحفوظة تبقى على الخادم مدة محدودة (أيام). المحادثة هنا قصيرة فلا مشكلة، لكن لا تبنِ نظاماً يعتمد على `previous_response_id` بعد أسابيع.

### المخرجات المهيكلة في المحادثة (تذكير بالدرس 2.5)

`ICPReport` يحتوي حقلين خاصين بالمحادثة:

- **`change_summary`**: "Initial proposal" في المرة الأولى، ثم ما تغيّر ولماذا. تقرأ سطراً واحداً فتعرف أثر ملاحظتك.
- **`questions_for_user`**: النموذج يسألك ما يحتاج معرفته. هذه الأسئلة غالباً أفضل ملاحظة تعطيها في الدورة التالية.

وحقل `why_fit` يطلب ربط كل سبب بحقل من الملف (`named_customers includes Al-Rajhi Bank`). هذا امتداد لفكرة التأسيس من الخطوة 1ج: الاستنتاج مسموح، لكن يجب أن يُبنى على حقيقة يمكن تتبعها.

وحقل `signals` له هدف عملي: الخطوة 3 ستقيّم قائمة شركات، وتحتاج علامات **يمكن رؤيتها من الخارج** لتحكم هل الشركة من الشريحة أم لا.

## شرح الكود

### `agents/icp.py`

| الدالة | دورها |
| --- | --- |
| `load_profile()` | يقرأ ملف الخطوة 1 ويتحقق من شكله. الملفات القديمة (قبل `named_customers` مثلاً) تعطي رسالة واضحة: أعِد الخطوة 1 |
| `propose_icp()` | الدورة الأولى: الملف كاملاً + `store=True` |
| `refine_icp()` | الدورات اللاحقة: الملاحظة + `previous_response_id` + التعليمات مرة أخرى |
| `_reasoning()` | يضيف `reasoning` فقط إن كان `REASONING_EFFORT` مضبوطاً |

قاعدة في التعليمات تستحق الانتباه:

```
- Trust target_customers_site and named_customers more than
  target_customers_external: the first two are what the company itself shows.
```

هنا تظهر فائدة فصل الحقول في الخطوة 1ج: الوكيل يعرف مصدر كل معلومة، فيعطي ما تقوله الشركة عن نفسها وزناً أكبر.

### `scripts/define_icp.py`

الحلقة الأساسية:

```python
report, response = propose_icp(profile)
...
while True:
    ...
    report, response = refine_icp(feedback, response.id)
```

`response.id` من كل دورة يصبح `previous_response_id` للدورة التالية. هكذا تتسلسل المحادثة.

## أخطاء شائعة وحلولها

| ما تراه | السبب | الحل |
| --- | --- | --- |
| `BadRequestError` يذكر `reasoning` أو `reasoning.effort` | `MODEL_REASONING` نموذج عادي | ضع نموذج استدلال، أو اترك `REASONING_EFFORT=` فارغاً |
| `BadRequestError` يذكر `minimal` | `o4-mini` لا يدعم `minimal` | استخدم `low` |
| `BadRequestError` يذكر `temperature` | لا يحدث هنا؛ إن ظهر فأنت تستخدم `MODEL_REASONING` في الخطوة 1 | راجع `MODEL_SMART` |
| `NotFoundError` يذكر `previous_response_id` | الاستجابة السابقة لم تُحفظ أو انتهت مدتها | ابدأ محادثة جديدة |
| `FileNotFoundError: Run step 1 first` | لا يوجد ملف الشركة | شغّل `analyze_company` أولاً |
| `ValueError: ... older step` | ملف الشركة من نسخة قديمة | أعد تشغيل الخطوة 1 |
| `RuntimeError ... incomplete` | التفكير استهلك الرموز | `--effort low` |
| الانتظار أكثر من دقيقة | `effort=high` أو نموذج كبير | طبيعي؛ جرّب `medium` |

## تمرين لك (25 دقيقة)

1. **قارن الاستدلال بعدمه:** شغّل مرة بـ `MODEL_REASONING=gpt-5-mini`، ومرة بـ `MODEL_REASONING=gpt-4o-mini` مع `REASONING_EFFORT=` فارغ. قارن `why_fit` و `assumptions`: أيّهما أدق في ربط الأسباب بحقائق الملف؟
2. **قارن نموذجي استدلال:** `gpt-5-mini` مقابل النشر `o1-mini` (الذي هو `o4-mini`). قارن الزمن، ورموز الاستدلال، والجودة.
3. **راقب نمو الإدخال:** بعد 3 ملاحظات، افتح `logs/calls.jsonl`. كيف تغيّرت `input_tokens` من دورة لأخرى؟ ماذا يثبت ذلك عن `previous_response_id`؟
4. **اكسر المحادثة عمداً:** في `refine_icp()` احذف سطر `instructions=INSTRUCTIONS` مؤقتاً، وأعطِ ملاحظة. هل ما زال يكتب `why_fit` مربوطاً بالحقول؟ أعِد السطر بعدها.

أرسل لي النسخة النهائية من الـ ICP وأرقام التمرين 3.
